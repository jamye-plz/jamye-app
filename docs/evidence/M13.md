`applyProfile`(`src/core/auth/auth-controller.ts`)은 네트워크/스토리지 I/O가 없는 **동기** 발행
primitive다. `disposed || !tokens || state.status !== "signed-in"`이거나, 발행하려는 profile의
`id`가 현재 `state.profile.id`와 다르면 no-op이다(다른 계정으로의 오발행 방지 가드). 마이크로태스크
지연이나 비동기 self-check는 없다 — `tests/core/auth/auth-controller.test.ts`의 `applyProfile`
describe가 이 가드와 "generation이 이미 진행된 뒤 호출하면 no-op"을 검증한다.

### Account deletion (U3 `DELETE /api/v1/me`)

| 시나리오                                | 근거                                                                                                                                                                                        |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| confirmation                             | `delete-account-section.test.tsx` "pressing delete account shows a destructive confirm and does not call deleteAccount yet" / "does not call deleteAccount when cancel is pressed" — destructive `Alert.alert` confirm이 `deleteAccount()` 호출보다 먼저 뜨고, 취소 시 미호출                    |
| blocker(409 `group_ownership_transfer_required`) | `account-lifecycle.test.ts` "returns 'blocked' and never calls logout on group_ownership_transfer_required"; `delete-account-section.test.tsx` "a blocked result shows guidance and re-enables the row (leaves the session untouched)" — 그룹 소유권 이전 안내 렌더, 행 재활성화, 세션 불변 |
| error                                    | `account-lifecycle.test.ts` "returns 'error' distinct from 'blocked'..."; `delete-account-section.test.tsx` "an error result shows retry guidance, and retrying calls deleteAccount again" — 재시도 안내 렌더, 행 재활성화, 세션 불변                    |
| retry                                    | `delete-account-section.test.tsx` "an error result shows retry guidance, and retrying calls deleteAccount again" — 1차 error 후 재확인으로 총 2회 호출 확인                          |
| 실제 구현된 local scope cleanup           | 아래 문단 참고                                                                                                                                                                           |

`deleteAccount()`는 `pushDisable.disable()`(토큰이 아직 유효할 때 best-effort 실행, 실패는 삼킴) →
`session.authorizedRequest(deleteAccount)` → 성공(204) 시에만 `session.logout()` 순서를 지킨다
(`account-lifecycle.test.ts`의 `invocationCallOrder` 비교로 검증). `session.logout()`이 호출된
이후의 local scope cleanup은 `tests/core/app-providers.test.tsx`의 A2 신규 테스트가
`AccountScopeController.setPrincipal(null)`과 notifications store의 `setPrincipal(null, null)`
실행을 확인한다. groups/chat/topics store의 principal-loss cleanup은 기존
remount-on-`[origin,userId,epoch]`-key 패턴(코드 리딩으로 확인: `groups-provider.tsx:36-37`,
`connected-chat-provider.tsx:40`, `topics-provider.tsx:50-53`)과 각 provider 레벨의 기존 dispose
단위 테스트(`connected-chat-provider.test.tsx:215` 등)로 뒷받침되나, 본 마일스톤에서
`app-providers.test.tsx` 수준의 전용 통합 테스트는 groups store에 한해 추가하지 않았다 — A2 결과
보고서가 명시한 **테스트 커버리지 갭**(코드 자체의 갭이 아니라 통합 테스트 갭)이다.

미디어 캐시(스테이징/다운로드 파일)는 `deleteAccount()`가 파일 삭제를 전혀 수행하지 않으므로
원 상태로 남지만, 모든 읽기 경로가 `authorizedRequest` 게이트를 요구하는 인증된 media 플로우이므로
로그아웃 이후에는 접근이 불가능하다(격리이지 삭제가 아니다).

`updateNickname`과 `deleteAccount`는 공유 in-flight 가드를 사용한다. 한쪽이 진행 중일 때 다른 쪽을
호출하면 `{status:'error', code:'in_flight'}`를 반환하며 네트워크 요청을 만들지 않는다
(`account-lifecycle.test.ts` "a concurrent updateNickname call while deleteAccount is pending..."
및 그 역방향 케이스).

## 미검증 / 별도 승인 필요

다음 두 항목은 이번 마일스톤에서 구현되지도, 자동 또는 수동으로 실행되지도 않았다. 각각 별도의
명시적 사용자 승인이 필요하며, 이 승인은 M13 구현 완료나 자동 검사 PASS로 대체되지 않는다.

1. **실제 계정 삭제 E2E** — 사용자 본인의 실계정을 대상으로 배포된 서버에 실제 `DELETE /api/v1/me`를
   호출하는 end-to-end 실행. 테스트 계정 생성 수단이 없으므로 자동 E2E는 fully mocked transport로만
   한정했다. 별도 명시 승인 후 사용자 본인 계정으로만 수행한다.
2. **파괴적 로컬 정리(destructive local cleanup)** — 삭제 전 principal의 SQLite namespace 파일과
   미디어 캐시(staged/downloaded)를 물리적으로 삭제하는 작업. `account-lifecycle.ts`는 이 삭제를
   전혀 수행하지 않는다(정적 확인: 파일-삭제 호출 없음). 계정 삭제 승인과 독립적으로, 별도의 명시적
   사용자 승인이 필요하다.

두 항목 모두 계획의 `prerequisites`와
`alternatives_considered.destructive_local_cleanup_of_deleted_namespace`에 명시된 대로 이번
plan의 구현 범위 밖이며, D1은 이 구분을 문서화할 뿐 어느 쪽도 수행하지 않는다.
