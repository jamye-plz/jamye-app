## 구현한 변경

- MD1 upload intent → 별도 object PUT → MD2 finalize와 MD3-MD5 조회·접근 port를 연결했다.
  계약 schema closure와 validators를 추가하되 서버 snapshot을 수정하거나 새 endpoint를 만들지 않았다.
- 시스템 이미지·동영상 선택과 기존 오디오 파일 선택, 파일 크기/MIME 허용 정책, 업로드 단계·취소·재시도를 연결했다.
  image-picker/document-picker/file-system/sharing을 추가했고 카메라·마이크 권한은 비활성화했다.
- 후속 형식 호환성 수정으로 `expo-image-manipulator`를 추가했다. HEIC 등은 native JPEG로 변환하고
  iOS 영상은 H.264/AAC MP4로 내보낸다. 출력에 기존 서버 제한을 적용하며 PUT·API·계약은 유지한다.
- 모든 첨부가 confirmed된 후에만 본문과 첨부 순서를 기존 SQLite/outbox에 원자적으로 저장한다.
  DB 저장 성공 후 선택 상태를 비우며 실패하면 유지한다. 텍스트 없는 visual 첨부와 단독 오디오도 지원한다.
- v005는 기존 메시지·outbox identity·lease·재시도 정보를 보존한다. C4 재시도는 같은 upload ID를 쓰고
  파일을 다시 업로드하지 않는다. Pending 첨부 ID를 canonical media ID인 것처럼 MD4/MD5에 전달하지 않는다.
- 대화의 canonical 이미지 표시와 첨부별 OS 열기·공유/저장, 작성자/그룹 소유자의 주제 이미지 첨부,
  MD3 페이지 조회·추가 업로드 후 주제 갱신을 연결했다.
- 후속 승인으로 송신 말풍선의 버튼 대비, MP4 영상 카드와 전체 화면 native 영상 재생을 추가했다.
  재생은 별도 버튼으로 시작하며 기존 OS 열기·저장은 유지한다.
- API bearer 요청과 object 전송을 분리했다. MD5는 API의 307 Location만 받아 허용 origin을 검사한 후
  별도 GET을 사용한다. 이미지도 bounded GET으로 받은 앱 임시 파일을 표시하며 signed URL을 Image에 주지 않는다.
- 화면 이탈·계정/대상 변경·background에서 전송을 취소하고 늦은 응답을 폐기한다. OS picker·share dialog와
  실제 background 전환을 구분한다. Staging/download 정리는 검증된 앱 소유 디렉터리의 파일만 대상으로 한다.

API/MD5와 GET의 `expo/fetch`·인증 분리·streaming file writer는 유지했다.
승인된 PUT 수정은 [로컬 Expo 모듈](../../modules/jamye-file-put/)만 추가한다.
iOS는 쿠키·credential/cache 저장소를 끈 ephemeral URLSession의 `uploadTask(fromFile:)`,
Android는 별도 OkHttp client와 8 KiB 파일 버퍼를 사용한다. JS에는 URL·파일 경로·MIME·크기만
전달한다. 자동 redirect는 금지하고 status만 반환한다. foreground 취소와 120초 timeout,
앱 소유 staging 파일·크기 검사를 유지하며 진행 UI는 시작/성공 완료만 표시한다.
새 범용 네트워크 계층·서버 계약·API endpoint·outbox·다운로드 변경은 없다.

## 영상 표시·기본 native 재생 보완 — 2026-09-14

## iOS 형식 호환성 보완 — 2026-09-11

사용자는 iOS 사진·영상 선택 후 HEIC/MOV 미지원 안내를 받았고 Android에서는 정상이라고 보고했다.
직전 읽기 전용 진단에서 iOS 선택 결과 두 파일은 실제 HEIC였다. 이름만 잘못 붙은 JPEG나 PUT 오류가
아니며, 원본을 그대로 반환하는 picker와 서버 형식 제한 사이에 호환성 처리가 없었던 것이 원인이다.

- `expo-image-manipulator ~57.0.16`을 SDK 57 권장 버전으로 추가했다. HEIC/HEIF·AVIF·TIFF·BMP 등의
  로컬 파일을 OS가 해독할 수 있을 때 JPEG로 재인코딩한다. MIME/확장자만 바꾸거나 원본을 삭제하지 않는다.
  사진 방향을 반영한 native 출력의 크기·치수와 JPEG 헤더를 확인한다. 지원 JPEG/PNG/WebP/GIF는 보존한다.
- iOS는 호환 표현 요청과 최대 1080p H.264/AAC MP4 내보내기를 사용한다. Android는 기존 system picker와
  MP4 경로를 유지하며 이미지 변환기만 공통으로 사용한다. 입력 코덱 해독 지원은 OS에 따라 다르다.
- 이미지 변환 입력은 로컬·최대 50 MiB, 최종 JPEG는 기존 10 MiB 제한을 적용한다. 동영상 출력은 기존
  50 MiB 제한이다. 전체 파일을 JS/base64로 복사하지 않고, JPEG 확인에는 앞의 3바이트만 읽는다.
- 파일 선택·변환 진행 문구와 중복 선택 방지를 연결했다. 늦은 결과·화면 이탈·계정 변경·거절·staging 실패
  시 새 변환 파일만 정리한다. OS 변환 자체의 즉시 취소나 앱 강제 종료 시 cache 정리 완료를 보장하지 않는다.
- 새 의존성의 정확한 버전·lock과 platform adapter 경계를 기존 품질 검사에 반영했다. 서버 snapshot·API·PUT
  모듈·기존 데이터는 변경하지 않았고 카메라·마이크 권한도 추가하지 않았다.

## 기존 Native 실패 기록과 후속 수정

M10 바이너리를 재사용하지 않고 clean prebuild 후 iPhone 17/iOS 26.5와
jamye_pixel_9_api_36/Android API 36에 새 바이너리를 설치했다. Mac LAN 주소가 변경되어 발생한
Metro 재접속 오류는 iOS `127.0.0.1:8081`, Android `10.0.2.2:8081` 연결로 복구했다.

앱의 실제 전송 모듈을 loopback synthetic endpoint에 연결해 양 플랫폼에서 다음을 관찰했다.
실계정 토큰·production media endpoint는 사용하지 않았다.

- 쿠키와 가짜 bearer를 먼저 넣은 대조 요청 성공.
- Manual 307의 status/Location과 서명처럼 인코딩된 query bytes 보존, redirect:error 거절.
- 객체 GET/PUT에는 cookie/bearer가 없음을 수신 서버에서 확인.
- 1 MiB GET의 파일 저장, 64 KiB File PUT의 바이트 전송.
- 스트리밍 도중 크기 초과 및 AbortSignal 취소 시 부분 파일 정리.

그 후 MIME assertion을 추가하자 **양 플랫폼 모두 실패**했다. `.bin` 이름에 명시적으로 지정한
`image/jpeg` 대신 iOS는 `application/macbinary`, Android는 `application/octet-stream`을 보냈다.
이는 형식 변환 테스트가 아니라 파일명과 무관하게 계약의 정확한 Content-Type을 보내는지 확인한
합성 바이트 전송이다. 잘못된 헤더는 실제 upload/finalize 실패로 이어질 수 있지만 production 실패를 재현한 것은 아니다.

설치된 `node_modules/expo/src/winter/fetch/RequestUtils.ts`는 File/Blob의 `arrayBuffer()`를 호출하고
Content-Type을 `body.type`으로 덮어쓴다. `node_modules/expo-file-system/src/File.ts`의 `arrayBuffer()`는
파일 전체를 읽는다. 따라서 최대 50 MiB 영상의 bounded-memory 업로드 기준을 충족하지 못한다.
이는 교체 전 Expo PUT 경로의 실패 기록이다. 1 MiB 다운로드 성공을 대용량 업로드 증거로 쓰지 않는다.

Native 로그는 `.agents/results/m11-native-probe-server-20260911.log`, 수신한 비밀 없는
요청 metadata는 `.agents/results/m11-native-probe-requests-20260911.json`에 보관한다.
임시 probe의 앱 import는 제거하여 `src/app/_layout.tsx`에 diff가 없고, loopback 서버도 종료했다.
Probe가 만든 원본·staging·download 파일만 정리했고 사용자 파일이나 기존 앱 데이터를 삭제하지 않았다.

독립 검토로 확인한 `File.upload()` 대안은 native 파일 전송·헤더·취소를 제공하지만
공개 옵션에 cookie 차단/no-follow 정책이 없어 그대로 대체하지 않는다.
또한 Android OS share promise 완료가 수신 앱의 파일 읽기 완료까지 보장하지 않는 문제는
미재현 위험으로 남긴다. OS 저장 결과와 안전한 임시 파일 수명은 별도로 확인해야 한다.

## 파일 선택 버튼 무반응 수정 (2026-09-11)

사용자가 주제 이미지·사진/동영상·음성 파일 버튼의 무반응을 보고했다. iOS 대화 화면에서
클릭은 전달되지만 공통 picker의 `runtime.isCurrent()`가 false여서 native picker 호출 전에
취소로 끝나는 것을 재현했다. 서버 API나 새 native PUT 모듈이 호출되기 전의 앱 상태 문제다.

실제 `MediaProvider`를 사용하는 회귀 테스트에서 StrictMode effect 재실행과 Suspense의
화면 숨김/복귀가 **정리된 lifetime을 재사용**하는 결함을 재현했다. `useMemo` 상태가 보존돼도
layout effect는 정리·재실행될 수 있다. 계정별 lifetime 슬롯을 두고 effect setup마다 새 lifetime을
연결하도록 고쳤다. 기존 lifetime은 영구 폐기하며, background·계정 변경·unmount 차단은 유지한다.
같은 패턴의 draft queue도 회귀 RED를 확인했다. React cleanup에서는 focus 해제·전송 취소·임시
draft 정리와 구독 해제를 수행하고, 재사용되는 engine을 영구 폐기하지 않도록 수정했다.
