## 4. 기기에서 찾은 결함과 수정

### 4.1 계정 DB v7 마이그레이션 실패로 주제·대화 저장소가 열리지 않음 (수정 완료)

- 증상: iOS에서 그룹 홈을 열면 `주제 저장소를 열지 못했습니다.`가 나왔다(사용자 보고). 운영
  API는 정상이었다.
- 원인(M15부터 있던 결함): expo-sqlite는 트랜잭션마다 새 연결을 여는데, 이 연결은 외래 키가
  기본값 OFF다. 그래서 대화방 정리·실패 메시지 버리기의 `ON DELETE CASCADE`가 한 번도 실행되지
  않아 고아 행이 쌓였고, 새 마이그레이션이 매번 실행하는 `PRAGMA foreign_key_check`에서 걸렸다.
- 수정(사용자 결정 U10 — 고아 행 정리만, 근본 원인은 후속): 마이그레이션 007이 재구성 전에
  applied_events → reconciliation_scopes → event_checkpoints → messages 순서로 고아 행을
  지운다. outbox 재구성은 메시지가 없는 command를 건너뛴다.
- 회귀 테스트: `media-expired-error-code-migration.bun.ts`의 `verifyDeviceOrphansAreRemoved`.
  RED(수정 전): `SQLite migration violated a foreign-key constraint.`, EXIT=1. GREEN: PASS.
  `tests/core/database/account` 12 suites / 61 tests PASS.
- 실제 DB 사본·기기 확인: 수정된 007을 기기 DB 사본에 적용하니 v7, FK 위반 0이 됐다(활성 계정
  outbox 16 → 15, 고아 1행 제거). 앱을 다시 실행한 뒤 iOS·Android 활성 계정 DB가 모두 v7로
  올라갔다.
- 후속 과제: 쓰기 연결에도 외래 키를 강제해야 한다. 켜기 전에 부모보다 자식을 먼저 쓰는 경로가
  있는지 점검이 먼저 필요하다(6절).

### 4.2 내가 보낸 공지 말풍선에서 주제 제목 링크가 보이지 않음 (수정 완료)

- 증상: iOS 기본 대화방에서 내가 쓴 공지의 제목 줄이 빈칸으로 보였다(`dev-05-ios-mainchat.png`).
- 원인: 링크 글자색이 `colors.primary`였는데 내 말풍선 배경도 같은 Berry였다.
- 수정: 링크가 말풍선 글자색을 물려받고 밑줄로 구분되게 했다(`chat-message-row.tsx`).
- 회귀 테스트: `chat-message-row.test.tsx`의 "in my own (primary) bubble the title stays
  readable". RED: 제목 링크 색이 말풍선과 같은 Berry(`#9B3F68`)였다. GREEN: 18/18.
- 기기 확인: Android 기기에서도 내 말풍선·받은 말풍선 모두 밑줄 제목이 잘 읽혔다(`dev-16`,
  `dev-28`).

주제(대화방 없음)는 영향받지 않는다.

## 6. 한계와 후속 과제

- 주제 공지 형식 흉내(VERIFY Step 7b, 사용자 결정 U14): 서버는 공지를 일반 `kind='user'`
  메시지로 저장하고, 앱은 본문 형식만 보고 제목을 링크로 그린다. 그래서 그룹 구성원이 같은
  형식의 본문을 직접 보내면 공지처럼 보이는 링크가 된다. 링크는 앱 안의 주제 경로로만 이동하고
  도착 화면이 권한을 다시 확인하므로 데이터 노출은 없다. 서버가 공지 구분값을 계약에 더하는
  후속으로 남긴다(로드맵 M17 (C)).
- 쓰기 연결 외래 키 강제: expo-sqlite의 새 연결은 외래 키가 기본 OFF다(4.1절). 쓰기 연결에
  `PRAGMA foreign_keys = ON`을 강제하기 전에, 부모보다 자식을 먼저 쓰는 기존 경로가 있는지
  점검이 먼저 필요하다.
- 과거 공지 소급 숨김 불가: 이번 업데이트 이전에 이미 처리된 `topic.deleted`는 로컬 이벤트
  기록에 공지 메시지 id가 남지 않아 식별할 수 없다. 새로 도착하는 `topic.deleted`만 처리된다
  (CHAT-AC2).
- Android 캐러셀 가장자리 항목이 여전히 사각: M3 캐러셀의 item mask가 RN 콘텐츠에 닿지 않고
  `@expo/ui`에 이를 조정할 API도 없다. 앱 쪽 고정 12dp 모서리는 완전히 보이는 항목에만 맞고,
  축소되는 항목은 기기에서 사각으로 잘려 보인다(사용자 결정 U7).
- 에뮬레이터 세션 복원이 3초 안전 타임아웃보다 느림: 이번 세션 측정으로 복원에 약 6초가 걸려
  로그인 화면이 잠깐 보였다. 복원 로직 자체는 M17 변경 밖이다. 실기기 복원 시간을 다시 재고,
  필요하면 복원 중 중립 화면이나 저장 순서 조정을 검토한다.
- Android 동영상 업로드 실패: 에뮬레이터 녹화(2.5MB H.264) 업로드가 네이티브 PUT(120초
  타임아웃)에서 끝나지 않아 실패했고 재시도도 실패했다(같은 경로의 사진 업로드는 성공). M17이
  바꾸지 않은 경로라 별도 조사가 필요하다.
- 뷰어 닫기 버튼 위치 불일치: 갤러리에서 연 사진 뷰어는 닫기가 오른쪽에 있고, 대화방 페이저
  뷰어는 닫기가 왼쪽·공유가 오른쪽이다. 기존 동작이며 UX 일관성 후속이다.
- 주제 목록 오프라인 오류 문구 중복: 전체 화면 오류 상태의 제목(`주제를 불러오지 못했습니다.`)과
  설명 첫 문장이 같다. 문구 다듬기 후속이다.
- Android 뷰어 닫기 스와이프는 adb `input swipe`/`motionevent`로는 재현되지 않았다(사람 손가락·
  마우스 드래그로는 확인됨, §3-4). M17이 만든 회귀는 아니지만 자동화 재현 수단은 남는 과제다.
- `auth-controller.ts` 분리 이후에도 `max-lines-per-function` lint 규칙은 추가하지 않았다
  (로드맵 F 묶음 참고).

### 2.3 Android 시작 ANR (C7-C9)

- 재현: 재빌드한 dev client에서 cold start 세 방식 × 2회, 총 6회를 돌렸다. 매 실행 전
  `adb logcat -c`와 `am force-stop`을 했고 실행 뒤 30초를 기다린 다음 logcat 전체와
  `dumpsys activity exit-info`를 모았다.

| 방식                                           | TotalTime / Displayed          | ANR |
| ---------------------------------------------- | ------------------------------ | --- |
| 1. `am start -n …/.MainActivity`(구성요소만)   | 2201 ms, 2006 ms(dev launcher) | 없음 |
| 2. `am start -a MAIN -c LAUNCHER -n …`         | 1476 ms, 1442 ms               | 없음 |
| 3. 런처 아이콘                                 | Displayed +1559 ms, +1561 ms   | 없음 |

  방식 1은 dev launcher 홈(`DevLauncherActivity`)만 띄우고 앱 번들을 불러오지 않는다. 방식 2와 3은
  `.MainActivity`가 두 번 표시된다(dev launcher가 마지막 번들로 `LAUNCH_SINGLE_TASK` 재시작).
  exit-info에는 `reason=6 (ANR)` 새 항목이 없고, `/data/anr`에도 새 파일이 없었다(production 이미지라
  `adb root`가 안 돼 내용은 읽지 못했다).
- 분석: M6(2026-09-09)의 `BIND APPLICATION ANR`은 현재 빌드에서 재현되지 않았다. 다만 6회 중 4회에서
  main thread `Choreographer: Skipped 32-36 frames`(약 530-600 ms)가 나왔다. 처음 repro 기록의 "일부
  실행(m2-2, m3-2)"은 과소 집계였고 분석에서 정정했다.
  - dev launcher가 원인 후보다. JS가 전혀 실행되지 않는 방식 1에서도 같은 크기의 지연이 `Displayed` 18ms
    뒤에 나온다. 소스상 `DevLauncherController.initialize`·`DependencyInjection.init`(동기
    `SharedPreferences` 오픈)과 launcher→app 전환의 `runBlockingOnMainThread`가 그 시간대에 main
    thread를 쓰지만, method-level trace가 없어 한 줄로 확정하지는 못한다.
  - MediaProvider의 동기 temp sweep은 배제했다. 이 코드는 JS thread(tid 5779)에서 돌고 Choreographer
    경고는 main thread(tid 5719)에서 나온다. 경고가 `ReactNativeJS: Running "main"`보다 1.4초 이상
    먼저 찍혀 sweep은 그때 아직 호출된 적도 없다.
  - release에는 이 경로가 없다. dev launcher의 해당 소스는 `expo-dev-launcher/android/src/debug/**`에
    있고 release 빌드에는 컴파일되지 않는다. release 측정은 하지 않았다(새 승인 필요).
- C9 계측: `__DEV__`에서만 도는 `[startup-timing]` 로그 세 가지를 넣었다(`start_to_first_screen`,
  `session_restore`, `temp_sweep`). 개인 값 없이 숫자와 고정 enum만 담는다. RED: 19개 중 2개 실패
  (이벤트 0건) → GREEN 19/19.
- 재확인: 같은 방식으로 6회를 다시 돌렸다. 한 회차(런처 아이콘 1회차)는 logcat 수집 실패로 판정을
  보류했고, 나머지 5회에서 ANR은 없었다. `temp_sweep`은 1-9 ms, `session_restore`는 2.3-3.7초였다. 3초 splash 안전 시간을 넘긴 회차는
  `trigger: timeout`으로 splash가 먼저 내려가 로그인 화면이 잠깐 보일 수 있다.
- 세션 중 dev-client 링크 처리 맥락에서 ANR과 크래시를 직접 관찰했다. 2026-10-01 23:11에 치환되지 않은
  `url=`로 링크를 연 뒤 약 2시간 된 프로세스가 크래시했고(`APP CRASH`), 2026-10-02 00:10에는 잘못된
  `url=`로 cold start하자 M6와 같은 `BIND APPLICATION ANR`(subreason 34)이 났다. 같은 조건의 재시험
  3건은 재현되지 않았고, 실험 사이 `adb logcat -c`로 crash 버퍼가 지워져 stack은 못 얻었다. 모두 debug
  빌드의 dev launcher 딥링크·번들 로딩 경로다. 이 때문에 Maestro flow는 시작 때 `stopApp`을 한다(2.4절).
- 결론: 일반 실행 경로에서 ANR은 재현되지 않았고, 앱 코드에서 고칠 원인은 없다(재현 전 추측 수정 금지).
  계측만 추가했다. 남은 일은 6절.

### 4.4 F-7 iOS 뒤로 버튼의 VoiceOver 이름이 route group 이름으로 노출됨 (수정 완료, F-7b는 결함 아님, 사용자 결정 A17·A21)

  `Back`은 JS 옵션이 아니라 이전 title(긴 그룹 이름)이 들어가지 않을 때 UIKit이 쓰는 시스템 문구다.

  | 기존(development region en) | 한국어 우선 | `뒤로` |
  | Korean-only(ko) | 한국어 우선 | `뒤로` |
  | Korean-only(ko) | 영어 우선(기본) | `Back` |

## 5. 한계와 후속 과제 (라운드 3)

- pending 업로드 sweep 없음: U4 뒤 PUT하지 않았거나 만료·U5 422로 끝난 pending 행과 객체는 사용자의 다음 U4나 계정
  purge 전까지 남는다(사용자당 최대 1행, 1 MiB 이하). 만료된 pending을 released로 바꾸고 삭제 큐에 넣는 주기
  sweep이 서버 후속 과제다.
- U6 rate limit key: peer 주소 기준이라 proxy 뒤에서는 실제 client IP별 제한이 아니다. 운영 값 6000회/60초는
  완화일 뿐이다. 신뢰 proxy가 넘긴 client IP 기준 key가 후속 과제다.
- U6 캐시: 응답은 `public, max-age=31536000, immutable`이다. id가 업로드마다 바뀌므로 교체·해제된 URL은 404(`no-store`)가
  되지만 이미 받은 클라이언트·edge 캐시에는 최대 1년 남을 수 있다.
- 서버는 JPEG 시그니처와 크기만 검증하고 디코딩하지 않는다. EXIF 제거는 앱의 512px JPEG 재인코딩이 맡는다.
- 로컬 서버 테스트 시계: 2.2절의 실패는 Podman VM 시계 어긋남이 원인이었다. 테스트 전 시계 차이 확인이나 DB
  시계 사용은 서버 (D) 묶음·task-16 후보다.
- SHIP UX 리뷰 후속: `기본 이미지로` 확인 단계(제공자 사진은 복구되지 않음), 사진 권한 거부 알림의 `설정 열기`,
  rate limit 재시도 대기 시간 표시, 업로드 진행 표시 scrim 대비(0.4 → 0.5). 새 메뉴의 VoiceOver·TalkBack·큰
  글꼴 확인은 코드로만 했다.
- `just contract-generate`가 현재 트리에서 거부되고 서버 validation 문서는 release-candidate generator를
  문서화한다. 둘의 정합 정리가 서버 후속 과제다. 계약 산출물은 문서화된 명령으로 재생성해 `just contract-check`를
  통과했다.
- 실기기 미확인: 이번 라운드에는 실기기 dev client를 빌드하지 않았다. 실기기에서의 아바타 업로드와 로컬 데이터
