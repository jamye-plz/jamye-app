# M1 실행 증거

- 마일스톤: M1 — 공식 mobile baseline과 Nix 전용 개발 환경
- 실행 기간: 2026-08-23 ~ 2026-08-24 (Asia/Seoul)
- 상태: 사용자 실행 명령 게이트, REFINE 후 진단, Ultrawork SHIP 검토 통과
- 증거 원칙: 사용자가 직접 공유한 결과만 PASS로 기록하고, 에이전트가 대신 실행한
  것으로 표현하지 않는다.

최종 devShell runtime 진단을 함께 M1 근거로 사용하며, 사용자는 이 상태의 M1 파일을
커밋하도록 명시적으로 지시했다.

## 3. 발견하고 해결한 회귀

첫 devShell 진단은 `17 passed, 4 failed`였다. Android 관련 두 실패는 설치 전 예상
상태였지만, Xcode 관련 두 실패는 Nix Darwin SDK setup hook이 interactive shell의
`DEVELOPER_DIR`와 `SDKROOT`를 덮어쓴 회귀였다.

`nix/dev-shell.nix`의 마지막 shell hook에서 외부 Xcode developer directory를 복원하고
build-only `SDKROOT`를 제거했다. 진단도 host `xcode-select`와 최종 환경을 분리 검사하도록
수정했다. 사용자가 새 devShell에서 재실행한 최종 결과 `23 passed, 0 failed`가 GREEN
회귀 증거다. 상세 원인과 수정 범위는 Ultrawork bug artifact에 남아 있다.

## 4. 소유권과 제외 범위 확인

- CLI build SDK의 원본은 Nix store의 composed Android SDK다.
- Android Studio가 관리하는 외부 SDK는 Emulator와 AVD에만 사용하며 devShell의
  `ANDROID_HOME`, `ANDROID_SDK_ROOT`, `PATH`에 섞지 않는다.
- Android license는 `android_sdk.accept_license = true`로 선언했다.
- `sdkmanager --licenses`, `ANDROID_NDK_ROOT`, NDK, Watchman, Maestro를 M1에 추가하지 않았다.
- Expo scaffold, `bun install`, native build, signing, store 제출을 실행하지 않았다.
- 기존 PWA, `jamye-server`, homelab, App Store Connect, Play Console을 변경하지 않았다.

## 5. 아직 이 증거가 보장하지 않는 것

- Expo SDK 57 template scaffold와 Bun/Metro 실제 조합
- iOS·Android development build
- simulator/emulator에 앱 설치 후의 runtime 동작
- production identifier, signing, credential, store 제출

이 항목들은 M2 이후의 별도 사용자 승인 게이트다.

## 6. Ultrawork 검토

VERIFY의 세 검토는 서로 대화 맥락이나 선행 verdict를 공유하지 않는 fresh-context
reviewer가 수행했다.

| 단계 | 관점 | 결과 |
|---|---|---|
| Step 6 | 승인된 M1 계획과 staged 구현의 1:1 정렬 | PASS |
| Step 7 | 위험한 쓰기, 비밀값, command injection, SDK authority, 외부 영향 | PASS |
| Step 8 | scope, 사용자 명령 소유권, Xcode 회귀 수정, Nix pin 회귀 | PASS |

CRITICAL, HIGH, MEDIUM finding은 없었다. Step 8이 보고한 LOW staging-state finding은
Serena가 같은 값으로 다시 기록한 `languages`와 `language_servers` 호환 목록이었다. 사용자가
이미 Serena 자동 변경 유지를 승인했으므로 최신 파일을 명시적으로 다시 staging했고, 남은
unstaged 경로가 없음을 확인했다.

REFINE에서는 fresh-context reviewer 두 명이 버전 중복과 문서 일관성 문제를 발견했다.
조치 후 별도의 fresh-context 재검토가 다음과 같이 통과했다.

| 단계 | 조치와 재검토 | 결과 |
|---|---|---|
| Step 9·11·13 | 큰 함수, 참조 영향, 새 dead code 확인 | PASS |
| Step 10 | `nix/toolchain-versions.nix`를 단일 버전 원본으로 도입하고 Android command-path 중복을 공통화 | PASS |
| Step 12 | Serena의 두 compatibility key가 함께 존재한다는 설명으로 교정 | PASS |

530줄 진단 스크립트는 모든 함수가 46줄 이하이고 redaction·결과 집계·조치 안내를 한 실행
흐름으로 공유하므로 파일 분할의 실익이 없다고 판정했다. 사용자 소유
`.agents/oma-config.yaml`의 `orchestrator.effort: max`는 그대로 보존했으며, 인접한 관리
주석은 `.agents/` SSOT 보호 규칙에 따라 에이전트가 수정하지 않았다.

이 REFINE은 devShell 평가 계약과 진단 환경변수를 변경했다. 사용자는 새 계약을 요구하는
최종 진단의 전체 통과를 보고했고 M1 파일의 커밋을 지시했다.

SHIP의 네 검토도 서로 독립된 fresh context에서 수행했다.

| 단계 | 관점 | 결과 |
|---|---|---|
| Step 14 | Bash/Nix/docs 품질과 적용 가능한 기계 검사 | PASS |
| Step 15 | devShell 진입, 진단 조치 안내, 사용자 gate, M2 경계 | PASS |
| Step 16 | Nix version contract 참조와 legacy/production 영향 | PASS |
| Step 17 | 비밀값, 환경변수, rollback, migration, signing, commit 준비 | PASS |

CRITICAL, HIGH, MEDIUM finding은 없었다. 일반 500줄 기준을 30줄 넘는 단일 진단 파일,
single-host output의 중복 방어 assert, REFINE 전 flake check라는 점은 LOW residual로
기록했다. 진단 파일은 REFINE의 독립 재검토에서 현재 응집도를 유지하기로 판정했고,
post-REFINE runtime 진단은 새 devShell 계약을 실제로 실행했다. 최종 검토에서 발견한
로컬 사용자 이름 경로는 `$REPO_ROOT`와 sibling repository 표기로 제거했다.

Application lint, TypeScript typecheck, test coverage, mobile E2E와 접근성은 통과로 가장하지
않았다. M1에는 Expo scaffold와 application code가 없으므로 적용할 수 없고 M2 이후의
명시적 gate다. 사용자는 M1 파일의 local commit을 최종 승인했다. M2, push, build,
signing, store 제출은 승인하지 않았다.
