# ADR 0015: 프로필 사진 호스팅과 계정 삭제 뒤 로컬 데이터 정리

- 상태: Accepted
- 결정일: 2026-10-06
- 적용 마일스톤: M17 (B)
- 대체하는 결정: [ADR 0008](0008-account-lifecycle-placement.md)의 결정 5(아바타 업로드 보류)와
  결정 6(파괴적 로컬 정리 전면 보류)

## 맥락

ADR 0008은 M13에서 프로필 수정과 계정 삭제를 앱에 연결하면서 두 가지를 의도적으로 보류했다.
결정 5는 아바타 업로드 UX를, 결정 6은 계정 삭제 성공 뒤 이전 principal의 SQLite 파일과 미디어
캐시를 물리적으로 지우는 일을 미뤘다. 결정 6은 "별도의 명시적 사용자 승인"을 조건으로 걸었다.

M17 라운드 3 (B)에서 사용자가 두 항목을 모두 진행하라고 요청했고, 로컬 정리는 "복구 가능 기간 30일이
지난 뒤"를 범위로 명시 승인했다(결정 B0, B3). 두 기능은 서로 다른 문제를 풀지만 같은 두 결정을 대체하고,
둘 다 계정 화면과 계정 lifecycle 위에서 구현되므로 하나의 ADR로 기록한다.

아바타에는 기존 경로에 걸림돌이 있었다.

- 채팅 미디어 파이프라인(M11, `src/features/media/platform/media-object-transfer.ts`)은 그룹 범위이고,
  서명 URL이 600초 뒤 만료되며, 서버의 `avatar_url`은 외부 https URL만 받는다.
- 앱의 아바타 지우기는 `null`을 보냈지만 서버는 `null`을 무시한다(no-op). 지우려면 `""`를 보내야 한다.

## 결정

### 1. 아바타 호스팅: 서버 전용 아바타 API(task-19)와 공개 불변 URL

- **채택**: 서버 task-19가 아바타 전용 업로드를 제공한다. U4(`POST /api/v1/me/avatar/uploads`)가
  업로드를 시작하고, 클라이언트가 presigned PUT으로 객체를 올리고, U5가 완료를 확정해 `users.avatar_url`을
  서버가 만든 공개 URL로 바꾼 뒤 `User`를 돌려준다. U6은 인증 없이 읽는 공개 URL이며 업로드마다 새로
  생기는 추측 불가 ID를 쓰고 바뀌지 않으므로 오래 캐시해도 된다. 앱의 아바타 표시 코드(iOS
  `JamyeAvatarView`, Android Compose `Image`)는 카카오·Google 프로필 사진과 똑같이 공개 URL을 읽으므로
  그대로 쓴다. 사진을 바꾸거나 지우면, 계정이 영구 삭제되면 이전 객체는 삭제 대기열로 들어가 지워진다.
- **기각한 대안 1**: 채팅 미디어 파이프라인을 재사용한다.
- **기각 이유 1**: 그 파이프라인은 대화방(그룹) 범위로 설계돼 있고, 서명 URL이 600초 뒤 만료되므로
  프로필 필드에 영구 저장할 수 없으며, 서버의 `avatar_url` 검증은 외부 https URL만 받는다. 셋 중 하나만
  어긋나도 계약을 바꿔야 하는데 셋이 모두 어긋난다.
- **기각한 대안 2**: 구성원 전용 인증 아바타 로더를 둔다(공개 URL 없이 인증 헤더로 읽기).
- **기각 이유 2**: iOS와 Android 양쪽에 새 네이티브 로더와 캐시가 필요하다. 기존 아바타 표시 코드를
  그대로 쓸 수 있다는 장점이 사라지고, 로더와 캐시를 두 플랫폼에서 따로 유지해야 한다.

### 2. 클라이언트 사진 처리: 시스템 정사각형 자르기, 항상 512px JPEG 재인코딩

- **채택**: 이미지 1장을 고르고(`allowsEditing: true`, `aspect: [1, 1]`) 항상 중앙 정사각형으로
  자른 뒤 512px 이하 JPEG(q0.85)로 다시 인코딩한다. 재인코딩이 EXIF(위치 정보)를 없애므로 위치 정보
  제거는 서버가 아니라 클라이언트의 책임이다. 1 MiB를 넘는 결과는 거부한다. 새 의존성은 없다
  (`expo-image-picker`, `expo-image-manipulator`, `expo-file-system`은 `platform/` 어댑터에만 둔다).
  기본 이미지로 돌리기는 U2에 `avatar_url: ""`을 보낸다. `null`은 서버가 무시하므로(no-op) 앱은 어떤
  경로에서도 `null`을 와이어에 내보내지 않는다. iOS는 `aspect`를 무시하므로 앱의 항상-중앙-자르기가
  보정한다.
- **기각한 대안**: 원본 그대로 업로드하고 서버가 변환·EXIF 제거를 맡긴다.
- **기각 이유**: 서버는 이미지 처리 의존성을 늘리지 않고 크기·content type만 검증한다. 원본이 기기를
  떠나기 전에 위치 정보를 없애는 편이 개인정보 면에서 안전하다.

사진 권한 안내 문구에는 프로필 사진 용도를 더했다(`app.config.ts`의 `photosPermission`).

### 3. 계정 삭제 뒤 로컬 데이터 정리: 문서 디렉터리 registry와 시작 시 비동기 sweep

- **기록(채택)**: U3 계정 삭제가 성공하면 logout 직전에 `{databaseName, deletedAt}`을 문서
  디렉터리의 버전 있는 JSON registry(`account-local-data-purge-v1.json`, version 1)에 기록한다.
  `databaseName`은 origin+userId 해시(`jamye-account-v1-<64hex>.db`)이고 원문 userId, origin, 이메일은
  저장하지 않는다. `deletedAt`은 기기 시계다. 기록 실패는 삼키고 logout을 계속한다.
- **정리(채택)**: 앱 시작 뒤 세션 복원과 계정 scope open이 정착하면 비동기 sweep이 기록 시각에서
  30일(30×24시간) 이상 지난 항목의 DB 본 파일과 `-wal`, `-shm`, `-journal`을 지운다. 동기 temp sweep
  경로와 ANR 계측 경로에는 넣지 않는다. 실패한 항목은 registry에 남겨 다음 실행에서 다시 시도하고
  사용자에게 오류를 보이지 않는다. registry의 이름이 패턴에 맞지 않는 항목은 버려서 변조된 파일로 임의
  경로를 지우지 못하게 한다.
- **보호 규칙(채택)**: 지금 열려 있는 principal의 DB는 지우지 않는다. 같은 principal로 다시 로그인해
  scope가 열리면(복구) 그 항목을 지워 예약을 취소한다. 취소, sweep, 계정 DB open은 하나의 mutex를
  공유해 삭제 I/O와 같은 파일의 open이 겹치지 않는다.
- **기각한 대안 1**: SecureStore에 기록한다.
- **기각 이유 1**: SecureStore(iOS 키체인)는 앱을 다시 설치해도 남는다. 그러면 DB 없이 항목만 살아남아
  의미 없는 예약이 쌓인다. 문서 디렉터리의 JSON은 앱 삭제와 함께 DB와 같이 사라진다.
- **기각한 대안 2**: 서버가 알려 주는 영구 삭제 시각을 기준으로 삼는다.
- **기각 이유 2**: 서버에 새 필드(계약 변경)가 필요하다. 사용자가 기기 시각을 쓰기로 정했고(B3) 앱만
  고치기로 했다.

기기 시계를 쓰는 데 따르는 비용은 아래 한계에 적는다.

## 결과

### 검증

- 앱 `bun run check:code` exit 0(격리 리뷰 수정 뒤 최종): Jest 255/255 suites, 2611/2611 tests, coverage
  statements 88.53% / branches 83.17% / functions 87.99% / lines 91.2%(threshold 80%), check-architecture
  위반 0.
- 서버 task-19(PR #18, merge `f86012e`)는 `just format-check`, `just clippy`, `just contract-check`,
  `just secret-check`, 전체 `just test`를 통과했고 운영에 두 단계로 배포됐다. migration 0019 적용(기능
  꺼짐), 꺼짐 smoke(U4·U6 404), 공개 URL 설정과 rate limit 상향(homelab), 활성 smoke(무인증 U4·U5 401,
  없는 U6 404 `avatar_not_found`)를 모두 통과했다. 앱 `contracts/server/openapi.json`은 서버 사본과 byte
  동일하다.
- 기기(iOS 26.5 시뮬레이터, Android API 36 에뮬레이터, 운영 서버):
  - 아바타: 사용자가 본인 계정으로 사진 선택 → 시스템 자르기 → 업로드 → 교체 → `기본 이미지로`를 확인했고
    Android는 비행기 모드의 실패 알림과 `다시 시도`도 확인했다. 교체·해제된 객체 5건은 공개 URL이 모두
    404이고 삭제 대기열이 모두 `succeeded`다.
  - 30일 정리: registry 시드로 31일 지난 항목은 DB와 `-wal`·`-shm`이 지워지고, 29일 23시간 항목과
    열린 계정 DB는 유지되고, 열린 계정의 항목은 scope open 때 취소됨을 두 플랫폼에서 확인했다.
  - 새 결함은 없었다. 상세는 [M17 evidence](../evidence/M17.md)에 기록한다.

### 한계

- 대화 행에 캐시된 `sender_avatar_url`은 다음 기록(history) 갱신 때 새 사진으로 바뀐다. 즉시
  갱신하지 않는다. 내 사진뿐 아니라 다른 구성원이 사진을 바꾼 경우에도 같다. 교체된 옛 URL은 U6가
  404를 돌려주므로 갱신 전까지는 이니셜(monogram)로 보인다.
- 이 기능 이전에 생긴 고아 DB(registry 기록이 없는 파일)는 건드리지 않는다.
- 다른 기기에서 계정을 복구하면 이 기기의 로컬 DB는 30일 뒤 지워진다. 서버에서 다시 동기화되는
  캐시이지만 이 기기의 아직 보내지 못한 outbox는 사라진다.
- 30일 기준은 기기 시계다. 시계를 크게 앞당기면 로컬 캐시가 일찍 지워질 수 있다(서버 데이터는 무관).
  정리는 앱을 시작한 뒤에만 일어나므로 앱을 30일 넘게 열지 않으면 그 뒤 첫 실행에서 지워진다.
- 마지막으로 시작했지만 끝내 U5로 확정하지 않은 업로드의 객체는 다음 업로드 또는 계정 영구 삭제
  때까지 남는다.
- 사진 내용 검수(moderation)는 없다.
- U6 공개 조회 rate limit은 프록시 뒤에서 모든 사용자가 한 버킷을 공유한다(운영 6000회/60초, 기본
  600회에서 상향). 실제 client IP 기준 제한은 후속 과제다.
- 기본 이미지로 돌리면 카카오·Google 제공 프로필 사진은 복구되지 않는다. 사용자에게 미리 안내했다.
- 업로드 진행률은 네이티브 PUT이 시작과 완료만 알려 주므로 퍼센트 없이 스피너로 표시한다.

### 롤백

- 서버: homelab `jamye-server.env`에서 `JAMYE_AVATAR_PUBLIC_BASE_URL`을 지우는 변경(PR #99 revert)으로
  U4-U6 route를 내린다. 업로드 시작·확정은 404가 되고 호스팅된 아바타 URL도 404가 되어 앱은 이니셜로
  보인다. migration 0019는 additive라 되돌리지 않는다(필요하면 배포 기록의 pg_dump로 복원).
- 앱: 이 라운드의 앱 변경은 하나의 브랜치로 묶여 있어 commit revert로 되돌린다. 되돌린 앱은 아바타
  메뉴가 없어지고 30일 정리를 하지 않는다. 이미 기록된 registry 파일(`account-local-data-purge-v1.json`)은
  읽는 코드가 없으므로 남아도 영향이 없다. 의존성(B7)과 사진 권한 문구가 함께 되돌아가므로 dev client를
  다시 prebuild·빌드해야 한다.
